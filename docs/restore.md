# Резервне копіювання та відновлення

## Що копіюється

| Дані | Де зберігаються | Як копіюються |
|---|---|---|
| База даних (контент, користувачі, ролі, журнал аудиту, версії) | том `pgdata` | `pg_dump` → gzip, `backups/reform-monitor-<UTC-дата>.sql.gz` |
| Завантажені файли (колекція `media`) | том `media` | `tar.gz`, `backups/media-<UTC-дата>.tar.gz` |
| Конфігурація (`.env`) | `/opt/reform-monitor/.env` | **вручну**, у менеджері паролів (у резервну копію не входить навмисно) |

Скрипт `scripts/backup.sh`: перевіряє цілісність архіву перед збереженням, виставляє права `600`, видаляє копії, старші за 14 днів (`RETENTION_DAYS`), за бажанням надсилає копію у зовнішнє сховище (`RCLONE_REMOTE`).

Розклад: cron, щодня о 02:15 — див. [deploy.md](deploy.md#8-резервні-копії).

## Відновлення

```bash
cd /opt/reform-monitor
ls -lh backups/
./scripts/restore.sh backups/reform-monitor-<дата>.sql.gz
```

Скрипт запитує підтвердження, зупиняє застосунок, очищає схему `public`, завантажує дамп, запускає застосунок, чекає на `healthy` і виводить кількість записів у ключових таблицях. Без запиту: `FORCE=1 ./scripts/restore.sh <файл>`.

Файли `media`:

```bash
docker compose exec -T app tar -C /app -xzf - < backups/media-<дата>.tar.gz
```

### Відновлення на новому сервері

1. Виконайте кроки 1–5 з [deploy.md](deploy.md), у `.env` поставте `SEED_ON_START=false`.
2. `docker compose --profile prod up -d`
3. Скопіюйте файл копії в `backups/` і запустіть `./scripts/restore.sh <файл>`.

`PAYLOAD_SECRET` може бути новим: наявні сесії стануть недійсними, користувачі увійдуть знову з тими самими паролями.

## Журнал аудиту і резервні копії

Таблиця `audit_log` захищена тригерами від `UPDATE`, `DELETE` і `TRUNCATE`. Відновлення працює, бо скрипт видаляє і створює заново всю схему (`DROP SCHEMA`), а це доступно лише власнику бази — тобто тому, хто має доступ до сервера, а не користувачеві адмінки. Копії зберігаються поза базою, тому журнал можна звірити з архівом за будь-який із 14 днів.
