# Імпорт даних із Google Sheets

Імпорт — це й механізм щоденного оновлення, і демонстрація **перенесення даних**: скрипт документований, перезапускається і не створює дублікатів.

## Джерело

| `GOOGLE_SHEET_ID` | Звідки читаються дані |
|---|---|
| порожній | локальні файли `data/sheets/<аркуш>.csv` (демонстраційні дані в репозиторії) |
| заданий | публічна таблиця Google Sheets, CSV-експорт кожного аркуша за назвою, без API-ключа |

Адреса експорту: `https://docs.google.com/spreadsheets/d/<ID>/gviz/tq?tqx=out:csv&sheet=<аркуш>`.

### Як підключити власну таблицю

1. Створіть таблицю Google Sheets із пʼятьма аркушами: `chapters`, `directions`, `benchmarks`, `measures`, `updates`.
   Найпростіше — імпортувати файли з `data/sheets/` («Файл → Імпортувати → Вставити нові аркуші») і перейменувати аркуші.
2. «Доступ → Усі, хто має посилання → Читач».
3. Скопіюйте ID з адреси таблиці (`/d/<ID>/edit`) у `.env`: `GOOGLE_SHEET_ID=<ID>`.
4. `docker compose up -d` (перезапуск застосунку з новим значенням).

## Структура аркушів

Перший рядок — заголовки. Обовʼязкові стовпці позначено **жирним**. Суфікси `_uk` / `_en` — переклади.

| Аркуш | Ключ | Стовпці |
|---|---|---|
| `chapters` | `number` | **number**, **title_uk**, title_en, description_uk, description_en, order |
| `directions` | `slug` | **slug**, **chapter** (номер глави), **title_uk**, title_en, description_uk, description_en, icon (`scale`, `shield`, `people`, `globe`, `lock`), order |
| `benchmarks` | `code` | **code** (напр. `IBM-23-01`), **direction** (slug), **text_uk**, text_en, source_title, source_url, order |
| `measures` | `externalId` | **externalId**, **benchmark** (code), **title_uk**, title_en, responsible_uk, responsible_en, deadline, **status**, evidence (URL через пробіл або `\|`), notes_uk, notes_en, tags (через кому) |
| `updates` | `externalId` | **externalId**, **measure** (externalId заходу), **date**, from, **to**, comment_uk, comment_en, source |

- **Статус**: код (`not_started`, `in_progress`, `done`, `partial`) або українська назва («не розпочато», «у процесі», «виконано», «виконано частково»). «Прострочено» задати не можна — воно обчислюється.
- **Дата**: `РРРР-ММ-ДД` або `ДД.ММ.РРРР`.

## Запуск

| Спосіб | Як |
|---|---|
| Кнопка | Адмінка → «Запуски синхронізації» → **Синхронізувати** (потрібне право запису на `sync-runs`) |
| Розклад | Щодня о 03:00 (Payload Jobs, завдання `syncSheets`); вимикається `ENABLE_JOBS=false` |
| CLI | `docker compose --profile tools run --rm tools pnpm migrate:sheets` |
| Перший старт | `SEED_ON_START=true` і порожня база |

## Гарантії

- **Ідемпотентність.** Запис шукається за ключем. Немає — створюється; є і відрізняється — оновлюється; збігається — лічильник «без змін». Повторний запуск на тих самих даних: `created 0, updated 0`.
- **Стійкість до помилок.** Помилковий рядок (невідомий статус, некоректна дата, посилання на неіснуючий орієнтир) пропускається, імпорт триває. Номер рядка, ключ і текст помилки записуються в `errors` запуску.
- **Історія статусів.** Якщо статус заходу в таблиці змінився, під час імпорту автоматично створюється запис у `status-updates` (той самий хук, що й при редагуванні в адмінці).
- **Журнал.** Кожен запуск зберігається в `sync-runs`: час початку й завершення, джерело, спосіб запуску, лічильники `created / updated / unchanged / skipped`, перелік помилок.
- **Аудит.** Усі зміни імпорту потрапляють до журналу аудиту.

Перевірено 22.11.2026: перший запуск на порожній базі — `created 62`; повторний — `created 0, updated 0, unchanged 62, skipped 0`. Те саме перевіряє автотест `tests/e2e/admin.spec.ts` («повторний імпорт не створює дублікатів»).

Імпорт не видаляє записи, яких немає в таблиці: видалення виконується вручну в адмінці й фіксується в журналі аудиту.
